# Интеграция с Битрикс24

## Принцип

Сделка не создается из HTTP-запроса менеджера. После ручного подтверждения в той
же транзакции создается запись Outbox. Фоновый агент забирает ее и вызывает REST.
Это предотвращает потерю подтверждения при сетевой ошибке и позволяет безопасно
повторять запрос.

Используются актуальные универсальные методы:

- `crm.item.list` — поиск ранее созданной сделки;
- `crm.item.add` с `entityTypeId = 2` — создание сделки;
- `crm.item.productrow.set` с `ownerType = D` — товарные позиции.

Устаревшие `crm.deal.add` и `crm.deal.productrows.set` не используются.

## Настройка

1. Создайте входящий вебхук в Битрикс24 от отдельного технического пользователя.
2. Дайте ему только необходимый scope CRM и минимальные права на сделки.
3. Передайте URL через secret storage как `SAFEAI_BITRIX24_WEBHOOK_URL`.
4. Отдельно задайте точное имя портала в `SAFEAI_BITRIX24_ALLOWED_HOST`.
5. Никогда не сохраняйте webhook URL в Git, базе заявок или административном UI.

Пример формата переменных приведен в `.env.example`; реальные значения туда не
записываются.

## Защита от SSRF

Клиент принимает только HTTPS, требует точного совпадения hostname с allowlist,
запрещает redirect, отбрасывает private/reserved IPv4 и закрепляет проверенный IP
в cURL через `CURLOPT_RESOLVE`. TLS-сертификат продолжает проверяться для исходного
hostname.

## Идемпотентность

В сделку передаются:

```text
originatorId = SAFEAI_B2B_REQUEST
originId      = публичный UUID заявки
```

Перед созданием выполняется поиск по этой паре. Если Bitrix24 успел создать
сделку, но ответ потерялся, повторная попытка найдет существующую запись и только
синхронизирует товарные позиции.

## Повторные попытки

- максимум 8 автоматических попыток;
- экспоненциальная задержка, не более 60 минут;
- `processing`, зависший более 15 минут, возвращается в очередь;
- после исчерпания попыток заявка получает `export_failed`;
- администратор может вручную повторить экспорт;
- в базе хранится только безопасный код ошибки, но не webhook и не ответ портала.
